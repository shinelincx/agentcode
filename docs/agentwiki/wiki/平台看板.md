# 平台常驻看板（P2 前移）

## 决策

用户 2026-11-11 指示：**把 P2 的常驻看板提前，与功能同步实现**。原方案（V2.2 §13）把观测界面的优先级排在 P2，本页记录将该能力前移到当前阶段的决策与实现。看板默认只读；2026-11-12 先增加 `--intake` 需求录入，随后按用户指示升级为管理控制台（`--control`）：网页提需求、审批 G1/G2/G3、监控各节点执行；同日再将各角色配置纳入控制台（`/config`，C-016）。

## 定位与边界

| 项 | 内容 |
| --- | --- |
| 是什么 | 本地管理面：读 `projects/<proj>/state.db`，展示任务、节点、审批、门禁、预算、用量；`--control` 时可在网页提需求、启动任务、审批 G1/G2/G3 |
| 不是什么 | 不是业务应用的 UI（river 的扑克室界面无关）；不是多租户/远程控制台（无鉴权，仅回环） |
| 写操作 | 默认无（`mode=ro`）。仅 `--control`/`--intake` 显式开启时允许写：新建任务、启动、审批、编辑角色配置（见下） |
| 依赖 | 读路径仅 Python 标准库（`http.server` + `sqlite3`）；配置页延迟导入 PyYAML（项目已依赖），不引入 FastAPI/前端构建链 |
| 监听 | 默认 `127.0.0.1:8879`，不对外暴露 |

## 实现

`platform/dashboard.py`：

- `snapshot(db, yaml)`：单次快照，供 HTTP 与 `--print` 复用（CI/巡检可直接取 JSON）。
- 每请求新建只读连接，避免长连接缓存掩盖 WAL 中的新写入。
- 配额与阈值从 `project.yaml` 正则读取（`monthly_quota` / `max_usage_per_task` / `thresholds`），读不到时回退默认值，不硬依赖 PyYAML。
- `platform/dashboard.py`：数据快照、控制动作、JSON API 与静态资源服务；不含任何内联 HTML/CSS/JS。
- `platform/console/`：静态前端（`index.html` / `styles.css` / `app.js` / `settings.js`），无 CDN、无构建链。
- 前端每 3 秒轮询 `/api/overview`；运行模式由 `GET /api/mode` 下发（只读 / 只读+录入 / 控制台），页面不再由后端替换常量注入。
- 静态路由只服务 `platform/console/` 内文件（`resolve` + `relative_to` 拒绝目录穿越），按扩展名返回 Content-Type。

端点：

| 路径 | 内容 |
| --- | --- |
| `/` | 控制台页面（`console/index.html`） |
| `/styles.css`、`/app.js` 等 | 静态前端资源（仅 `platform/console/`） |
| `/api/mode` | 运行模式：`{control, intake, mode, default_project}`，前端据此显示提需求/审批入口并选默认项目 |
| `/api/projects` | 已注册项目列表 `{projects:[{name,label,db,yaml}], default}`（`projects/<name>/` 下有 `project.yaml` 或 `state.db` 即纳入） |
| `/api/search?q=&status=&limit=` | 按任务 id / 需求关键字与状态检索（按项目路由，最多 500 条） |
| `/api/overview` | 全量快照 JSON（budget / counts / tasks / node_runs / leases / outbox / lanes / gates / approvals / pending_approvals / usage_by_model / buffer_pending / task_steps / gate_states / gate_artifacts） |
| `/healthz` | `{"ok":true}` |
| `/intake` | SPA 别名：返回 `index.html`，前端路由到「操作」页（仅写模式） |
| `POST /api/intake` | 建任务 + 写 `requirement.json` + 保存参考图片（仅写模式，容忍 base64 大请求体） |
| `/api/jobs` | 控制台最近 20 个执行任务（queued/running/done/failed） |
| `/api/task/detail?task_id=` | 任务详情：节点时间线、门禁、审批、四类产物、原始需求字段与图片附件 |
| `/api/attachment?task_id=&name=` | 需求参考图片（限任务目录内 PNG/JPEG） |
| `/api/artifact?task_id=&kind=` | 需求/设计/测试/部署报告正文（限任务目录内） |
| `POST /api/task/start` | 启动任务（仅 `--control`） |
| `POST /api/task/decide` | 审批 G1/G2/G3，`decision=approved|rejected`；驳回必填 `reason`（1~2000 字，仅 `--control`） |
| `POST /api/task/rerun` | 从指定节点重跑，body `{task_id, from}`；挂起闸门时拒绝（仅 `--control`） |
| `/config` | SPA 别名：返回 `index.html`，前端路由到「设置」页（只读可看，`--control` 可改） |
| `/api/config` | GET 当前配置 + 可选项 + 最近审计；POST 保存（仅 `--control`，`X-Control: 1`） |
| `--print` | 终端打印同一份 JSON 后退出 |

多项目路由：除 `/api/mode`、`/api/projects`、`/healthz` 与静态资源外，所有 API 都接受 `?project=<name>`（GET）或请求体 `project` 字段（POST，优先于 query）；缺省用 `default_project`（`--project` / `AGENTCODE_PROJECT`，默认 `river`）。项目名只接受单段目录名，经 `resolve()` + `relative_to(PROJECTS_DIR)` 校验，`../` 等越界或未注册项目一律 404。

## 写模式：结构化需求录入（A2 intake，2026-11-12）

用户选择「网页表单」作为需求 intake 形态。为不破坏看板只读原则，写能力作为**显式开关**引入：

```
python platform/dashboard.py --intake
```

| 防护 | 实现 |
| --- | --- |
| 绑定 | 仍仅 `127.0.0.1`，不提供 `--host` |
| 跨站写入 | 必须带 `X-Intake: 1` 自定义头；跨源请求触发 CORS 预检，而服务不响应预检（`OPTIONS` → 405） |
| Origin | 若带 `Origin`，必须为 `http://127.0.0.1:<port>` 或 `http://localhost:<port>` |
| 体积 | 提需求（`/api/intake`）1~12MB（容纳最多 4 张 ≤2MB 图片的 base64）；其余写接口仍为 1~64KB，超限 413 |
| 字段 | `platform/intake.py` 校验：标题 ≤120、目标 ≤2000、验收标准 1~12 条、非目标 ≤2000、范围 lane∈{be,fe}、优先级∈{high,normal,low}；参考图片 ≤4 张、单张 ≤2MB、仅 PNG/JPEG 且文件头须与声明一致；失败 400 且**不落库** |
| 落库 | `tasks.requirement` = 归一化需求文本（含 `## 参考图片` 列表）；`<ws>/<task_id>/requirement.json` = 结构化全量（含附件元数据与 created_at）；图片正本在 `<ws>/<task_id>/attachments/` |

执行链路（表单创建后）：

```
python platform/run_task.py <task_id> start      # 需求→需求文档→G1
python platform/run_task.py <task_id> approve    # G1→设计→G2
python platform/run_task.py <task_id> approve    # G2→实现→测试→部署→G3
python platform/run_task.py <task_id> approve    # G3→retro→done
python platform/run_task.py <task_id> status     # 查看挂起节点与产物路径
```

`run_task.py` 在 `review_g1/review_g2/review_g3` 挂起时按产物摘要登记 `approvals`，approve/reject 同时写审批结论；实现节点在 `state.lanes` 缺省时解析 `DESIGN.md` 文件归属表自动生成 lanes（`feat/<task8>-<lane>`），intake 任务无需手写任务脚本。

执行链路为 `requirements → review_g1 → design → prototype → review_g2 → implement → test → deploy → review_g3 → retro`，控制台流程胶囊同步为 10 步（新增「原型」）。

| 项 | 内容 |
| --- | --- |
| 触发 | `DESIGN.md` 归属表含 `fe` lane → 生成；归属表存在但只有 `be` → 跳过（不再看关键词，避免「不涉及界面」等否定表述误判）；归属表缺失时才用界面关键词兜底 |

### G3 批准之后与 retro 的现状（2026-11-12 代码核对）

| 分支 | 行为 |
| --- | --- |
| G3 `approved` | `tasks.status=running` → `goto retro`（`approved_g3=True`） |
| G3 `rejected` | `goto implement`（`approved_g3=False`），随后 test → deploy → G3 依次重跑，deploy 新起 attempt |
| deploy 显式跳过（`deploy_skipped=true`） | 不经过 G3，直接 `goto retro` |
| deploy 失败（无 `deploy_report`） | `END`，任务停在 `gate_failed`，不进入 retro |

`retro` 节点（[graph.py](../../../platform/graph.py) `retro_node`）当前只做三件事：

1. 终态守卫：任务为 `awaiting_human` / `gate_failed` / `failed` 时直接返回，不改状态（防止把预算暂停或交付失败掩盖成 `done`）。
2. 以租约方式登记一次 `node_runs(node_name='retro')` 并关闭为 `done`（账本可追溯、可并发接管）。
3. 把 `tasks.status` 置为 `done`、`current_node='retro'`，随后到 `END`。

即 retro 是**流程盖章点**而非内容生成：它不写复盘报告，也不往 `retro_queue` 插入条目。V2.2 §10.3 的 Retro 记忆回写（L0 自动采纳 / L1 留池 / outbox 投递）由独立 CLI `platform/memory.py adopt|deliver` 完成，需人工或运维单独触发；看板「Retro 投递」面板读的是 `retro_queue`，其数据不由图节点产生。该差距属已知未接入项，不是本次部署失败的成因。

## 管理控制台（`--control`，2026-11-12）

用户要求把只读看板升级为管理控制台：网页提需求、网页审批、监控各节点执行。

- 启动：`python platform/dashboard.py --control`（`--intake` 为兼容别名）。默认仍只读；控制台要求回环地址与 `--db <project>/state.db`，启动时校验 langgraph 依赖。
- 提需求：`GET /intake` 表单新增「创建后立即启动」，创建成功后可一键入队 `start`，无需切 CLI。
- 审批：`POST /api/task/start` 与 `POST /api/task/decide`（approved/rejected）。复用 `run_task.py` 的闸门映射与产物 sha256 绑定；HTTP 立即返回 `202 + job_id`，图执行在后台单线程队列串行完成，页面轮询 `/api/jobs`。
- 重跑：`POST /api/task/rerun`（`{task_id, from}`）与任务详情「从节点重跑…」按钮，入口节点集合与 `run_task.py rerun --from` 一致。
- 自动登记审批：动作结束若挂起在 G1/G2/G3，控制台按产物哈希自动登记 pending 审批并把任务转为 `awaiting_human`，待审批区立即出现「批准/驳回」。CLI 启动的任务要到下一次 approve 才登记，控制台放行 `running` 状态并在图状态层做最终判定。

### 驳回理由与上游修订回环（R1，2026-11-13）

用户指示：人工审核节点拒绝时必须填写理由，由上一步的 Agent 判断是否根据退回原因生成新的方案。

| 环节 | 实现 |
| --- | --- |
| 必填 | `/api/task/decide` 与 `run_task.py reject --reason`：驳回缺理由 400；理由归一化空白后 1~2000 字 |
| 入账 | `approvals.reason`（schema 新列，旧库 `ALTER TABLE` 增量迁移），`decide_approval(..., reason)` 写入 |
| 回环 | 图内 G1/G2/G3 驳回本就回上游节点；现在通过 `ledger.latest_rejection_reason()` 取最近驳回理由写入图状态 `rejection_reason`，并把任务转回 `running` |
| 判断 | `requirements-gen`/`design-gen` 模板（1.3.0/1.2.0）新增 `$rejection_feedback` 与约束：Agent 先判断反馈是否成立——成立则修订产物，不成立则保留原文并注明分歧；两种情况都输出完整文档 |
| 留痕 | 修订时记 `requirements_revise`/`design_revise` 门禁结果（含轮次与理由摘要）；审批表可看每轮理由 |
| 防失控 | 每闸门回环上限 `MAX_REVISES=5`（图状态 `revises_g1/g2/g3` 计数），超限记 `revise_limit_*` 门禁失败并终态 `rejected`，防止无限回环烧预算 |
| 前端 | 驳回按钮弹「驳回」模态（textarea + 确认驳回），空理由不放行；已决审批表与任务详情新增「理由」列 |

- 监控：任务表内渲染 9 步流程胶囊（需求→G1→设计→G2→实现→测试→部署→G3→retro）；「详情」弹窗展示节点时间线、门禁、审批与四类产物；产物正文通过 `/api/artifact` 读取（路径必须位于任务目录内）。
- 配置消费（2026-11-12）：任务表新增「SLA」列——`awaiting_human` 任务按 `updated_at` 计算等待小时并与 `gates.G1/G2/G3.sla_hours` 比较，超时标红；`budget.max_inflight_tasks` 在控制台 `start` 入队与 CLI `run_task.py start` 处拦截（满额返回 409 / 退出非 0）；`budget.thresholds` 经 `ledger.configure_thresholds` 参与预算状态判定。
- 防护：写请求必须带 `X-Control: 1`（intake 兼容 `X-Intake: 1`）且 Origin 白名单；仅绑回环；请求体 ≤64KB（提需求因携带 base64 图片放宽至 12MB）；非法结论/驳回缺理由 400、状态冲突 409、重复入队 409。

并发与语义：

- 进程内单线程队列串行执行；同一任务已有排队/执行中的动作时拒绝再次入队。
- 与 CLI 混用没有跨进程互斥：同一任务不要同时从两个入口推进。checkpointer/账本能拒绝明显冲突（如图状态已存在或无挂起闸门），但不保证排队顺序。
