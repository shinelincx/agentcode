# 项目概览

仓库包含多 Agent 软件交付平台、评审 HTML、V2.0 历史方案和 V2.1 修订方案。2026-11-11 整理时，V2.0 已全文读取，原评审 HTML 仅做结构级阅读，当时 V2.1 仍待评审。平台随后已有实现与回归，参见 [[wiki/P1实施进度]]、[[wiki/P2规划]] 和 [[wiki/平台看板]]。

最新综合方案复用 [[wiki/方案演进]]，以该 Markdown 为编辑源生成 HTML 阅读版。修订聚焦执行恢复、预算预占、权限落地、审批绑定、不可变发布及十二项故障验收场景。历史版本与替代原因保留，不把文档升级等同系统升级。

正式需求与任务状态以 GitHub Issues 为准，正式领域及架构决策遵循领域文档与 ADR。2026-11-16 使用 `gh issue list --state open` 查询未返回开放条目。

证据：[[sources/项目资料]]、[[sources/V2.1技术核验]]。关联：[[wiki/方案演进]]、[[wiki/待核实问题]]。

## 平台架构评审（2026-11-16）

评审基线为 `3ffd905`。最近 16 次提交里，`ac_regression.py` 变动 8 次，`graph.py`、`dashboard.py`、`console/app.js` 各变动 5 次。重点沿 CLI、控制台、任务图、账本和原始需求目录追踪。有关项目预算事后计量、业务账本与检查点分离的约束见 [[wiki/V2.2修订]] 和 [[wiki/方案演进]]。下方保留评审时的提案与基线，实施授权与结果另列。

### 当前框架

- Python 通过 LangGraph 编排需求、设计、原型、实现、审查、测试、部署和复盘，G1/G2/G3 通过 interrupt 挂起与恢复。每个项目用 SQLite `graph.db` 持久化图检查点、用 `state.db` 记录业务事实、用项目目录保存产物和配置。参见 [graph.py](../../../platform/graph.py) 第 1749–1799 行、[schema.sql](../../../platform/schema.sql) 和 [[wiki/节点规则]]。
- CLI 与 Python 标准库 HTTP 控制台是任务操作的两个 adapter。静态 JS 提供六个视图；项目 YAML 配置角色、模型、门禁和预算；Worker 处理 Codex CLI、Git 与命令执行。现有技术栈能承载下列修正，首轮建议集中在模块职责。参见 [run_task.py](../../../platform/run_task.py)、[dashboard.py](../../../platform/dashboard.py)、[worker.py](../../../platform/worker.py) 和 [[wiki/角色配置]]。

### 改进提案与验收

1. **项目执行 module（Strong，首选）。** 控制台只在编译图缓存缺失时设置 `RIVER_WS` 与计量缓冲路径，保存配置也会切换全局项目。真实控制台队列的临时探针按 A→B→A 执行，最后一次 A 使用了 B 的工作区、账本路径和配额。另用双项目、桩 Worker 恢复 A 的 G1，触发 SQLite 外键错误，B 中未出现 A 的任务行。先让每次动作绑定目标项目，再把检查点、配置、账本路径和计量归到同一个深 module。删除测试表明，只移除全局锁会失去串行约束，项目绑定仍缺少所有者。提高 locality，两个 adapter 共享隔离的 leverage。验收覆盖普通图和重跑图缓存的 A→B→A，以及保存 B 配置后继续 A。核对双方实际任务 UUID、产物、预算和模型。现有 `MULTI-01` 手工切换项目，且用标签比对 UUID 列，需补正常入口断言。参见 [dashboard.py](../../../platform/dashboard.py) 第 592–648、910–933 行、[graph.py](../../../platform/graph.py) 第 108–110、1062–1112 行及 [ac_regression.py](../../../platform/ac_regression.py) 第 2103–2207 行。
2. **人工审批 module（Strong）。** CLI 和控制台各自维护闸门产物映射，复用待审记录时未比对当前摘要，登记结论后直接恢复图。桩 Worker 测试中，G1 待审稿改动后，旧摘要仍被批准，流程推进到 G2。把现有的产物摘要、审批结论、驳回理由及检查点恢复规则集中到一个 module。删除测试支持移除两份重复编排，账本与检查点仍各有职责。通过同一行为 seam 验证，CLI 与 HTTP adapter 共享规则的 leverage。验收覆盖正常批准、过期产物、重复提交、账本已登记而恢复中断，明确恢复语义和用户看到的产物版本。现有 AC-09 覆盖账本查询，G2/G3 的产物变化需再从任务入口验证。参见 [run_task.py](../../../platform/run_task.py) 第 78–91、141–158 行、[dashboard.py](../../../platform/dashboard.py) 第 504–520、649–667 行、[ledger.py](../../../platform/ledger.py) 第 480–519 行及 [[wiki/P2规划]]。
3. **控制台项目视图 module（Worth exploring）。** Node 替身控制响应顺序时，切到 B 后迟到的 A 总览替换了 B 的显示数据。现有代码还在附件编码前后重新读取当前项目，创建与自动启动分成两次请求；实际错投未进行浏览器端到端验证。让项目选择、轮询、详情和写入链路在同一个 module 内管理项目身份与响应有效期。删除测试支持把散落的异步检查集中，否则每个调用方都得独自处理切换。可控网络 adapter 提高测试 leverage，响应与项目关联集中后提高 locality。验收覆盖切换期间读取、附件加载、创建与自动启动，以及页面上的旧响应丢弃。参见 [app.js](../../../platform/console/app.js) 第 44–65、435–465、621–634、691–725 行和 [settings.js](../../../platform/console/settings.js) 第 19–34 行。
4. **原始需求录入 module（Worth exploring）。** 任务行先提交，附件及 `requirement.json` 后写。故障注入使后者失败时，账本里留下可见的 `pending` 任务。让现有录入 module 负责完整交付与失败恢复，并集中需求 Agent 与 G1 展示对原始记录和附件的读取语义。删除测试表明，录入模块承载真实的校验与写入职责，应该深化；可移除重复的读法。CLI、HTTP adapter 共享成功与失败语义的 leverage，历史格式和附件布局的 locality 更高。验收覆盖首张或后续附件写入失败、记录写入失败、重试、旧版结构化记录和旧账本纯文本。参见 [intake.py](../../../platform/intake.py) 第 140–164 行、[ledger.py](../../../platform/ledger.py) 第 262–271 行、[dashboard.py](../../../platform/dashboard.py) 第 415–461 行及 [graph.py](../../../platform/graph.py) 第 368–391 行。

### 四项修复结果（2026-11-16）

1. **项目执行。** 每次 `ControlRunner.execute` 在进程锁内先绑定工作区和计量缓冲并刷新预算，再读取或运行图。普通图和重跑图都在相同约束下执行。配置保存刷新和 CLI 切项目复用工作区绑定。MULTI-01 使用真实 UUID 核对账本隔离，覆盖 A→B→A 和保存 B 配置后复用 A 的重跑图。相关代码见 [graph.py](../../../platform/graph.py) 和 [dashboard.py](../../../platform/dashboard.py)。
2. **人工审批。** CLI 与控制台共用 [task_approval.py](../../../platform/task_approval.py)。审批记录按图检查点关联轮次，旧库增量补列。当前产物摘要变化时，本次结论被拒，更新待审版本后重新查看和审批。控制台提交审批记录 ID 与摘要，旧按钮或旧请求无法批准下一轮。结论已入账、图仍停在同一闸门时，CLI 或 HTTP 可用相同结论和理由恢复，冲突结论被拒。APPROVAL-01 覆盖 G1 文档、G2 原型变化、重复 G1 结论与中断恢复。
3. **控制台项目视图。** 切换时清空旧数据并关闭旧弹窗，总览、队列、设置、查询与详情按项目或页面版本接收响应。附件预览带项目参数，提交时绑定项目与自动启动选项，后续两次写请求使用同一项目。Node 四例验证响应乱序、A→B→A、设置回填和附件编码期间切换。证据见 [前端回归](../../../platform/console_project_test.js)。
4. **原始需求录入。** [intake.py](../../../platform/intake.py) 在项目内暂存附件和原始记录，完整落盘后以目录重命名发布，再提交可见任务行。正常失败清理暂存或已移动的目录。CLI、需求 Agent 与 G1 展示复用原始记录和附件读取，保留旧结构化记录、历史附件目录及账本文本回退。INTAKE-01 注入两张附件、记录和账本提交失败，验证清理、重试以及两类旧记录兼容。

Windows 本地使用 CI 直接依赖版本复跑 [AC 回归](../../../platform/ac_regression.py) 得 314 通过、0 失败、2 既有跳过。图冒烟 12/12、基础冒烟 20/20、Prompt 黄金用例 17/17、Node 4/4 全通过，Node 回归已加入 [CI](../../../.github/workflows/agentcode-checks.yml)。本机 Chrome 配合临时双项目和桩 Worker，验证迟到总览、附件提交与自动启动、草稿保留，以及过期 G1 批准被拒与新版提交推进到 G2。

验证范围为临时工作区与本机回归。真实模型、实际 staging 部署、CLI 与控制台跨进程争用和强制杀进程恢复仍待验证。文件与 SQLite 跨介质发布在强停时可能留下尚未提交任务行的目录，该目录无可启动任务记录。远端 GitHub Actions 尚未运行本次变更。
